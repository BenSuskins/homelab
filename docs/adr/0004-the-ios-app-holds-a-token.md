# The iOS app holds a token, and `gh` becomes a macOS-only transport

The macOS menu bar app's defining property is that it holds no credential: every GitHub call shells out to `gh`, so `gh auth login` is the entirety of its credential management and there is nothing in the app to leak. iOS has no subprocess spawning — `Process` is unavailable to a sandboxed app — so an iOS companion cannot inherit that property. It has to authenticate on its own or not exist.

Decided: the iOS app authenticates with **GitHub's OAuth device flow** and stores the resulting token in the Keychain under `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, and `gh` is demoted from "the way this app talks to GitHub" to "the macOS implementation of `GitHubTransport`". The seam moves up one level: `GitHubClient` stops building argv and starts building a `GitHubRequest`, which `GhCommandTransport` renders as `gh api …` on macOS and `URLSessionTransport` sends to `api.github.com` on iOS. The macOS app keeps its no-token property unchanged; it is now a property of one transport rather than of the design.

Device flow was chosen over a pasted fine-grained PAT because it needs no client secret and therefore no server, the token can be revoked from GitHub's own UI without touching the device, and the enrolment is an eight-character code rather than a credential handled in a phone's clipboard.

**The cost is that this is a broader grant than the macOS app ever needed.** Device flow issues **classic** scopes only, so `repo` + `workflow` reaches every repository on the account, where a fine-grained PAT could have been scoped to `BenSuskins/homelab` alone. Against that: the token is Keychain-bound to one unlocked device, and every write — `trigger`, `cancel`, `merge` — is gated behind `LAContext` biometrics, because a credential that deploys Ansible to six hosts and squash-merges to `main` is a deploy button in a pocket. Reads are not gated; a status glance should not cost a Face ID prompt. If GitHub ever ships fine-grained scopes for device flow, swapping to them is a change inside `TokenStore` and nothing else.

The alternatives were a pasted fine-grained PAT, which is narrower but is a long-lived secret rotated by hand and typed into a phone; a GitHub App with an installation token, which is correctly scoped but needs a server to hold the private key and exchange it, which is a service to run and back up for one personal app; and abandoning native iOS for a PWA behind Traefik, which needs no GitHub credential at all because it would proxy through something on the tailnet — but it reuses none of `HomelabCore`, and loses widgets, Shortcuts and biometrics along with it.

## Amendment: the macOS app holds one too, and `gh` is gone

The decision above preserved the menu bar app's no-token property by making `gh` one transport of two. That property is now given up deliberately: both apps authenticate with the same OAuth client and the same device flow, `GhCommandTransport`, `CommandRunner` and `GitHubCommandLineRunner` are deleted, and `URLSessionTransport` is the only production implementation left.

Decided on consistency: one sign-in flow to build, test and reason about instead of two credential stories that diverge in exactly the place bugs hide. What tipped it beyond consistency is that the `gh` transport carried a cost the token does not — a GUI app launched from Finder inherits none of your shell's environment, so `GitHubCommandLineRunner` searched `PATH`, then Nix, then Homebrew, then `/usr/local` by hand, and every "works in my terminal, not from the Dock" report would have landed there. `Session` moves into `HomelabCore` and both apps use it.

**The cost is that the Mac now stores a credential it did not, and stores it worse than the phone does.** `make bundle` ad-hoc signs, so every build carries a different signature and macOS can treat the rebuilt app as a different one for Keychain purposes — the same mechanism that already drops the login item registration on reinstall. Expect to sign in again after a rebuild until the app is signed with a real identity. `gh` never had that problem, because the credential belonged to `gh` and not to us. Two smaller costs: the contract tests read the Keychain rather than `gh`'s stored login, so they skip when nobody has signed in on that machine, and the token is a classic-scope grant across every repository on the account where `gh`'s was too, but at least was one the user already knew about.

Keeping `gh` on macOS was the alternative, and it was defensible right up until the second app existed: it is strictly the more secure arrangement, and this amendment is a considered trade of that for a single code path. A third option — try `gh`, fall back to device flow — was rejected for adding a selection to test and a failure mode (a `gh` login that expires mid-session) on top of both paths it was meant to simplify.

## Note: nothing expires, so being asked to sign in again is a bug

Expiring user tokens and refresh tokens are a GitHub *App* feature — 8-hour access token, 6-month refresh token, opted into at registration. This is an OAuth App, so the device flow returns an `access_token` and nothing else, and that token does not expire; `DeviceFlow` decodes no `refresh_token` because GitHub never sends one.

So a prompt to enrol again means the grant was revoked on github.com, or the app threw the credential away. It did the latter for a while: `URLSessionTransport` reported both "the Keychain read returned nothing" and "GitHub replied 401" as `notAuthenticated`, and `Session.handleIfUnauthenticated` deletes the Keychain item on that. Since the item is `WhenUnlockedThisDeviceOnly`, any poll overlapping the screen locking read nothing and cost the user their token — a re-enrolment roughly once a day. The two are now separate cases and only a real 401 signs you out.
